# Project Shimmer

## A. What Shimmer is

Shimmer is a constitutional multi-agent system for reviewing regulated documents,
such as competition-law instruments and procedural regulations. It is multilingual,
including Arabic and other right-to-left scripts. A fixed roster of LLM agents works
across four stages (read and extract, verify and audit, redact, amend), and the whole
system is governed by an append-only constitution. Producers and auditors are always
different model families, so no model checks its own work. The output of a run is a
set of reviewed deliverables: flagged provisions, cited findings, and proposed
amendments, each grounded in an operator-defined convention and a precise reference
into the source corpus.

Shimmer does not invent new machine-learning mechanisms. It composes established ones
under a governance frame. See section I for positioning and references.

## B. The constitutional model

Shimmer is governed by seven seed laws. They are not guidelines; they are enforced,
and they are amended only by a formal, append-only process (see vocabulary below). The
agents propose changes; only the operator ratifies; agents never self-apply.

- LAW-0, Operator sovereignty: the operator is the sole source of constitutional
  authority. No agent may create, amend, or repeal a law.
- LAW-I, Do no harm to the source: no agent may alter, fabricate, or suppress source
  content. Agents may flag, annotate, and footnote.
- LAW-II, Know your bounds: each agent has a fixed capability set; it may request
  another agent's service but never perform it.
- LAW-III, No self-audit (cross-family verification): no model may verify or audit
  output generated by its own model family. Claude-produced content is audited by GPT
  or by local models, and the audit trail records which model produced and which model
  verified every segment.
- LAW-IV, Protect what is private: sensitive content (PII, classified material,
  institutional secrets, and content marked for redaction) must be processed only by
  offline agents on local hardware. No sensitive content may cross a network, enter an
  API call, or leave the operator's machine. This law cannot be overridden by any
  later legislation, precedent, amendment, or operator instruction; it outranks LAW-0
  for this scope, because a single leak is irreversible.
- LAW-V, Remember before you act: before any search, verification, or computation an
  agent consults the constitution, then precedent, then memory.
- LAW-VI, Structure is earned, not assumed: organizational structure below the Top
  Orchestrator emerges from identified work through chartered task forces.

## C. Vocabulary

- INFRA-NNN: a ratified constitutional amendment (an act). It is recorded in the
  constitution and is append-only: an id is never reused, never inserted between
  existing ids, and never renumbered.
- DELTA: a proposed amendment (a bill) before the operator ratifies it. Agents may
  draft and propose a DELTA; only the operator ratifies it; agents cannot enact one.
- CONV-*: an operator-defined convention, that is, a rule the review applies (for
  example a confidentiality rule that marks certain spans as sensitive).
- REF-*: a precise citation into the corpus (an article or section reference). Every
  amendment finding must cite at least one CONV-* and at least one REF-*.

## D. Architecture

Eighteen fixed-role agents collaborate across four stages on an append-only message
bus. Each agent emits one flat, per-item envelope to the bus; consumers read by
reference, and a later revision of an item supersedes an earlier one. Context for each
agent is assembled per provision through retrieval over a reference index (semantic
retrieval when an embedding store is present, term matching otherwise).

The roster and its model split:

- Read and extract: PROCESSOR (Claude Sonnet) drafts; LEGAL_ANALYST (Claude Opus),
  ARCHIVIST and CITATION_RESOLVER (Claude Sonnet), and INST_FINDER, STYLE_GUARDIAN,
  and SPEECH_ACT_TAGGER (Claude Haiku) organize, analyze, and tag.
- Verify and audit: VERIFIER, FACT_CHECKER, and PRACTICE_AUDITOR (all GPT-4o). These
  audit Claude-produced content, satisfying LAW-III cross-family verification.
- Redact: REDACTOR (local Qwen 2.5 7B Instruct), the only agent permitted to handle
  sensitive content, running offline.
- Amend: AMENDMENT_DRAFTER (Claude Opus) assembles the canonical amendment master, and
  a six-rank editorial review board reviews it: EDITOR_CLERK, EDITOR_HEAD_OF_UNIT, and
  EDITOR_HEAD_OF_SECTION (Claude Opus) below, EDITOR_HEAD_OF_DEPARTMENT,
  EDITOR_DEPUTY_DG, and EDITOR_DG (GPT-4o) above. The board is advisory and escalates
  rank by rank under a bounded loop.

The pipeline runs end to end in this real execution order (the phase numbers are the
project's own labels, not a renumbered sequence):

1. BOOT: load the constitution and message bus, spawn learning assets from the context
   corpus, parse conventions into a registry, and build the reference index.
2. Date cascade and cutoff: date the corpus and populate `input/operational/` from
   `input/context/` according to the review scope.
3. Phase 3-4, content production: PROCESSOR drafts per document.
4. Phase 5, verification and fact-check: the GPT auditors review the drafts.
5. Phase 5.5, convention review: the conventions are applied to the provisions.
6. Phase 6, synthesis: AMENDMENT_DRAFTER assembles the deliverable master.
7. Phase 6.5, editorial review board: the six ranks review the clean master.
8. Phase 7: any DELTA proposals are surfaced to the operator.
9. Phase 9, redaction screening: always runs (LAW-IV is strict).
10. Phase 8: persist artifacts and write the run summary.
11. Run end: the learning engine captures provisions, rebuilds its graph, and updates.

Multilingual support is built in: per-document language detection drives per-language
embedding-model selection and direction-aware output for right-to-left scripts such as
Arabic.

## E. The sensitivity layer (LAW-IV in practice)

Shimmer treats LAW-IV as a working capability, not a slogan. Sensitive spans are
defined by the operator's conventions (CONV-*), never judged by a model. When a run is
declared sensitive, the masking layer engages at every point where content would cross
to a network or an API: the sensitive spans are held on the local machine and replaced
in the outbound payload by typed placeholders (for example a redacted identifier or a
redacted figure), so the raw content never leaves the machine. Every masking decision
is appended to an exposure ledger under `durable/governance/`, which is the LAW-IV
audit trail and records the field masked and the operator rule that authorized it,
never the content itself.

This layer is operator-activated. It is off by default; the operator declares a
sensitive run to switch it on. The local Qwen redactor, the only agent allowed to see
sensitive content, applies the operator's redaction rules locally on every run.

## F. The learning engine

Shimmer keeps a cross-run ontology graph under `ontology/`. After each run it captures
the run's provisions, conventions, citation forms, and document structure, rebuilds a
graph of those nodes and their relationships, and updates a small graph neural network
incrementally. The graph accumulates across runs, so recurring patterns become visible
over time.

The engine is proposal-side only: it can surface recurring patterns that an operator
may choose to ratify as an amendment, but it never changes the system on its own. It is
payload-free under sensitive mode: it stores abstractions (ids, counts, categories,
typed placeholders), never raw sensitive spans.

## G. Setup (from a blank slate)

Prerequisites: Python 3.9 and git.

1. Clone the repository.
2. Install the base dependencies MANUALLY, before running setup:

   ```
   py -3.9 -m pip install -r requirements.txt
   ```

   `setup.bat` does NOT install the base dependencies. It launches the preflight
   bootstrap (`scripts/preflight.py`), which checks your API keys, installs the two
   small optional libraries (beautifulsoup4 and langdetect) if missing, checks the
   local Qwen backend and pulls its weights if absent, and runs a soft GPU check.
   Preflight deliberately does NOT install torch (the correct wheel is platform and
   CUDA specific); `requirements.txt` pins it, so the manual install above covers it.

   The declared dependencies are: pypdf, python-docx, lxml, beautifulsoup4, fpdf2,
   sentence-transformers, numpy, langdetect, ddgs, and torch.

3. Place your API keys in an external `config.py` OUTSIDE the repository (keys never
   live in the repo). Shimmer locates it via `$SHIMMER_CONFIG_PATH`, then a sibling
   `../api_keys/config.py`, then the repo-root `.env_path` pointer. The key loader
   reads key values only (ANTHROPIC and OPENAI are required, BRAVE is optional). Model
   selection is owned by the agent registry, never by the key file.
4. Ensure the local Qwen redactor is available (`Qwen/Qwen2.5-7B-Instruct` with torch
   and transformers). It runs offline and handles sensitive content.
5. Run setup to see the readiness report:

   ```
   setup.bat
   ```

First-time setup is slow and that is expected, not a fault. Installing dependencies and
pulling the Qwen model weights (several gigabytes) plus the multilingual embedding model
can take several minutes or longer. Do not interrupt them; later runs reuse the
installed packages and cached weights.

## H. Running Shimmer

The required path:

1. Put the documents to review in `input/context/`.
2. Put at least one convention in `input/conventions/` (a markdown file with CONV-*
   rules, for example a confidentiality rule). Redaction acts only on compiled operator
   rules, so a run with sensitive content needs a convention that marks it.
3. Run the pipeline:

   ```
   py -3.9 scripts/pipeline.py --non-interactive
   ```

4. Read the results in `output/runs/<id>/`: the per-document amendment deliverables, the
   append-only message-bus log, the audit and proposal artifacts, and the run summary.

You can follow a run live:

```
py -3.9 scripts/bus_viewer.py --follow
```

Optional, concrete variants (use the real flags):

- Non-sensitive run (the default): the pipeline refuses to start with the sensitivity
  layer inactive unless you declare the run non-sensitive. Add
  `--sensitivity-layer-inactive-override` (each use is logged to the governance ledger):

  ```
  py -3.9 scripts/pipeline.py --non-interactive --sensitivity-layer-inactive-override
  ```

- Sensitive run: the operator activates the sensitivity layer (`LAYER_ACTIVE` in
  `scripts/sensitivity_layer/`). The masking layer then engages at every network egress
  point, holding operator-marked spans local and sending typed placeholders, with the
  exposure ledger recording each masking. No override is needed once the layer is active.

- Redaction waiver: if the local Qwen redactor is unavailable, or you consciously
  declare a run non-sensitive with no redaction, add `--no-redaction-override` (logged
  to the governance ledger).

- Other flags: `--max-docs N` limits the number of operational documents,
  `--run-objectives "..."` sets the run intent, `--skip-model-check` skips the live
  deprecated-model gate, and `--save-snapshot NAME` / `--load-snapshot NAME` /
  `--reset-snapshot` / `--list-snapshots` manage the learned state.

A run writes everything under `output/runs/<id>/` so runs never overwrite each other.
The verification gate (`py -3.9 -X utf8 scripts/verify_session1.py`) checks the system
end to end and is the standard pre-run health check.

## I. Related work and positioning

Shimmer composes established mechanisms; the contribution is the composition plus the
amendment-governance framing, not novel mechanisms. It sits in two lineages.

Multi-agent debate and cross-family verification:

- Du, Y., Li, S., Torralba, A., Tenenbaum, J. B., Mordatch, I. (2023). Improving
  Factuality and Reasoning in Language Models through Multiagent Debate.
  arXiv:2305.14325. (ICML 2024.)
- Liang, T., et al. (2023). Encouraging Divergent Thinking in Large Language Models
  through Multi-Agent Debate. arXiv:2305.19118.
- Chang, E. Y., Chang, E. Y. (2025). Multi-Agent Collaborative Intelligence:
  Dual-Dial Control for Reliable LLM Reasoning (MACI). arXiv:2510.04488. (Debate as a
  budget-aware, provably terminating controller using a cross-family LLM judge; the
  basis for constitution-as-controller and bounded rounds.)

Runtime governance and information-flow control:

- Zhong, P. Y., Chen, S., Wang, R., McCall, M., Titzer, B. L., Miller, H.,
  Gibbons, P. B. (2025). RTBAS: Defending LLM Agents Against Prompt Injection and
  Privacy Leakage. arXiv:2502.08966. (Adapts information-flow control to tool-based
  agents.)
- ARM: enforcing provenance invariants at the execution boundary. arXiv:2604.04035.
  (Execution-boundary provenance enforcement, the lineage LAW-IV sits in.)

Positioning: Shimmer composes multi-agent cross-family verification (the multi-agent
debate lineage) and runtime information-flow control (the IFC lineage) under an
append-only, operator-ratified constitution with a formal amendment process, applied to
defect-intolerant multilingual regulated document review. The mechanisms are
established; the contribution is the composition and the amendment-governance framing.
LAW-IV is an information-flow locality law with a per-item exposure ledger as its audit
trail.
